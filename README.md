# FGPbot 2.0 — один канал, один локальный процесс

Бот для одного локально настроенного Twitch-канала. Принимает чат через
EventSub WebSocket, отвечает через Twitch Send Chat Message API, хранит состояние
в локальном SQLite. Для запуска не нужны Docker, VPS, внешняя база, публичный
веб-сервер или аккаунт стримера.

**При обновлении установленной копии см. [инструкцию](UPGRADE.md).** Сохраняй
существующие `.env` и `data/tokens.db`; смена версии Python не требует новой
OAuth-авторизации при действующих токенах и достаточных правах.

## Обычный запуск на Windows

Из папки проекта, после сохранения своего `.env`:

```powershell
.\setup.bat
.\selftest.bat
.\runtwitchbot.bat
```

`setup.bat` выполняет `uv sync --locked --no-dev`: устанавливает зафиксированные в
`uv.lock` runtime-зависимости (`aiohttp`, `msgspec`, `python-dotenv`) в `.venv`.
Поддерживается Python **3.14.x**. Установка требует `uv` в PATH.
Обычный запуск **не обновляет зависимости и не запускает установку**.

Для разработки выполните `uv sync --locked`, затем `prek install --hook-type pre-commit
--hook-type pre-push`. Команды проверки и безопасного исправления доступны через
`just --list`, `just check` и `just ci`.

`selftest.bat` использует временные базы и локальные HTTP/WebSocket-серверы.
Настоящий Twitch, свои `.env` и `data/tokens.db` для тестов не используются.
Зависимости предварительно должны быть установлены.

`authorize-bot.bat` нужен для первоначальной авторизации, замены скомпрометированных
токенов или выдачи новых разрешений, а не при каждом включении компьютера. Откроется
браузер: войти нужно **в аккаунт бота**, не стримера. Проверяются ID аккаунта,
Client ID приложения, разрешения и одноразовый OAuth state.

В Twitch Developer Console redirect приложения должен совпадать с настройкой:

```text
http://localhost:4343/oauth/callback
```

По умолчанию запрашиваются только `user:read:chat` и `user:write:chat`. Пароль
приложению не передаётся: вход и согласие происходят на странице Twitch.

Запущенный бот не открывает локальный HTTP-порт. Callback-порт открывается только
командой `auth`, только на loopback и максимум на время авторизации.

## Linux

Основной пользовательский launcher пока Windows-first, но Python runtime не привязан к
Windows. GitHub Actions запускает типизацию и полный автоматический test suite как на
Windows, так и на Ubuntu. На Linux зависимости можно установить через
`uv sync --locked --no-dev`, а бот запустить командой `uv run python main.py run`.
OAuth callback, EventSub и SQLite используют кроссплатформенный Python-код; отдельный
Linux service/launcher в проект пока не входит.

## Проверка без открытия Twitch

### Тихая проверка состояния

```powershell
.\status.bat
# Или без паузы, для терминала / другой программы:
.\.venv\Scripts\python.exe main.py status
.\.venv\Scripts\python.exe main.py status --json
```

Это чтение локального `data/status.json`, **без сетевого обращения и сообщений в
чат**. Состояние обновляется примерно каждые пять секунд. Файл старше двадцати
секунд считается `STALE`, даже если в нём раньше было написано `READY`.

| Состояние | Значение |
|---|---|
| `READY` | Токен пригоден, WebSocket получает служебные данные, есть подписка на нужный чат, обработчик не завис, нет известных актуальных ошибок отправки. |
| `DEGRADED` | Есть известная проблема: отправка, обработка, проверка API, сквозной тест либо недавняя потеря событий из очереди. |
| `CONNECTING`, `SUBSCRIBING`, `RECONNECTING` | Подключение ещё не готово или восстанавливается. |
| `AUTH_REQUIRED` | Нужно исправить авторизацию / разрешения. Бот перечитывает базу и сможет заметить новые токены. |
| `STOPPED`, `FAILED` | Процесс корректно остановлен либо завершился с ошибкой. |
| `STALE`, `NOT_RUNNING`, `UNKNOWN` | Свежего достоверного состояния нет. |

Показываются число обработанных сообщений, команд, успешных API-отправок,
ошибок, потерь очереди и время последних событий. `last_error` — последняя
зафиксированная ошибка; она может быть исторической после восстановления.
Доступность музыкального сервиса и followage выводится отдельно от основного чата.

**`READY` не равен доказательству сквозной доставки.** Для этого есть отдельный
показатель `e2e`: `UNVERIFIED`, `WAITING_FOR_ECHO`, `CONFIRMED` или `FAILED`.
`CONFIRMED` относится ко времени последней проверки, а не ко всем будущим сообщениям.
После обычного нового подключения сквозная проверка снова считается непроведённой.

### Сквозная проверка одним сообщением

При уже запущенном боте:

```powershell
.\check-chat.bat
# Тот же вызов без pause:
.\.venv\Scripts\python.exe main.py check-chat --send
```

**Эта команда публикует одно видимое диагностическое сообщение в целевом чате.**
Самостоятельно на старте и по таймеру такие сообщения не отправляются.

Проверка проходит путь:

```text
локальная заявка → запущенный бот → Send Chat Message API
→ Twitch → EventSub → очередь → обработчик диагностической команды
→ совпадение message_id и одноразового маркера → PASS
```

Ответ API должен содержать `is_sent=true`, а входящее событие — совпадающий
`message_id`, аккаунт бота и целевой канал. Чужая команда `!fgpcheck`, случайный
маркер, другой ID сообщения или состояние от прошлого процесса не дают `PASS`.
Проверен и случай, когда входящее событие приходит раньше HTTP-ответа отправки.

Нет подтверждения — `FAIL`, а не оптимистичное `OK`. Автоматической повторной
публикации после неоднозначного сетевого сбоя нет. Интервал между заявками — минимум
30 секунд. Проверка не подтверждает работу музыкального провайдера, всех команд,
отображение сообщения на каждом клиенте или его сохранность после модерации.

### Дополнительная диагностика

```powershell
.\.venv\Scripts\python.exe main.py doctor
.\.venv\Scripts\python.exe main.py doctor --offline
```

`doctor` проверяет актуальную авторизацию бота, канал и серверный список подписок
текущей сессии. **Не публикует сообщения и не обновляет OAuth-токены.** Поэтому
истёкший access token может дать ошибку doctor, хотя бот умеет восстановить его
через refresh. `doctor --offline` проверяет только локальные предпосылки; его код
успеха не означает, что Twitch доступен или сохранённый токен ещё действителен.

## Конфигурация и совместимость

Старые имена переменных сохранены:

```dotenv
TWITCH_BOT_APP_CLIENT_ID=your_app_client_id
TWITCH_BOT_APP_CLIENT_SECRET=your_new_app_client_secret
TWITCH_BOT_ID=1293258394
TWITCH_OWNER_ID=494679299
TRULA_MUSIC_TOKEN=your_music_service_token
```

Это шаблон: строки `your_...` нужно заменить локально своими значениями, не
отправлять в чат. Существующий `.env` не заменяй целиком примером.

Можно явно закрепить канал отдельно от старой переменной OWNER:

```dotenv
TWITCH_CHANNEL_ID=494679299
FGP_PROXY_URL=http://127.0.0.1:12334
FGP_LOG_LEVEL=INFO
FGP_LOG_CHAT=true
FGP_GREET_STREAM=true
FGP_CHAT_RETENTION_DAYS=0
```

Без `TWITCH_CHANNEL_ID` используется `TWITCH_OWNER_ID`, как в старой конфигурации.
Изменение `.env` требует перезапуска. Обновление пары токенов через `auth` бот
подхватывает из базы без обязательного перезапуска, если сам Client Secret и другие
настройки не менялись.

Прокси по умолчанию сохранён прежний — `http://127.0.0.1:12334`. Он явно передаётся
HTTP-запросам, OAuth и WebSocket. Чтобы использовать прямое соединение или системный
TUN, задай **пустое** значение `FGP_PROXY_URL=`. Глобальные `HTTP_PROXY` /
`HTTPS_PROXY` приложение не изменяет и не использует как неявный fallback.

`FGP_LOG_CHAT=false` отключает сохранение новых текстов чата, но не удаляет прежнюю
историю. Нулевое `FGP_CHAT_RETENTION_DAYS` сохраняет историю без автоудаления.
Положительное значение включает удаление записей старше заданного числа дней;
это осознанное изменение политики хранения, а не обязательный шаг обновления.

Все пути вычисляются от папки проекта, не от рабочей папки Планировщика заданий.

## Команды чата

| Команда | Назначение |
|---|---|
| `!ping`, `!пинг` | Ответ `Pong!`, проверка обработки команды зрителя. |
| `!help`, `!commands`, `!команды` | Список основных команд. |
| `!discord`, `!ds`, `!дс`, `!дискорд` | Ссылка Discord. |
| `!telegram`, `!tg`, `!тг`, `!телеграм` | Ссылка Telegram. |
| `!followage [логин]` | Срок фолловинга, если выданы соответствующие права. |
| `!currentsong`, `!трек` | Первый непрослушанный трек по данным Trula. |
| `!queue`, `!очередь`, `!q` | Непрослушанные треки, ограниченные длиной сообщения Twitch. |
| `!ban`, `!бан`, `!удалить`, `!забанить` | Только шуточный ответ. Реальных банов нет. |

Сохранены исходные ссылки канала; переопределяются через `FGP_DISCORD_URL` и
`FGP_TELEGRAM_URL`. Регистр команд не важен. На пользователя установлен интервал
3 секунды между известными командами; отправки сериализованы с паузой минимум
1,6 секунды. Сбой одного ответа не запускает цикл из сообщений об ошибке ответа.

Trula API сохранён из оригинального проекта. Кэш очереди — пять секунд, используется
общая HTTP-сессия. Когда сервис недоступен, команда отвечает об этом, а не молчит.
Если все треки отмечены просмотренными, старый первый трек больше не выдаётся за
следующий. Соответствие «первый непрослушанный = сейчас играет» унаследовано от
исходника: без более точного контракта провайдера это не независимое доказательство
фактического воспроизведения.

Генератор шуточных банов упрощён: встроенные варианты вместо `ultimate_responder`.
Команда больше не запрашивает весь список чаттеров и не требует права читать его.
Можно указать существующий Twitch-логин; присутствие человека в текущем чате не
проверяется. Самобан, бот и стример имеют отдельные ответы.

### Дополнительные права для followage

Для обычного чата токен стримера **не нужен**. Для followage нужен
`moderator:read:followers` у владельца канала либо у бота, который является
модератором этого канала.

Когда бот уже назначен модератором, авторизуй **бота** с дополнительным scope:

```powershell
.\.venv\Scripts\python.exe main.py auth --followers
```

Альтернатива — авторизация владельца канала:

```powershell
.\.venv\Scripts\python.exe main.py auth --account broadcaster
```

Второй вариант требует входа владельца **на машине, где запущена команда**.
Нельзя просто переслать стримеру localhost-ссылку: она укажет на его компьютер,
не на этот бот. Ради базовых команд делать это не требуется.

## Восстановление и ограничения

Обычный разрыв WebSocket приводит к новому подключению и новым подпискам.
Служебный `session_reconnect` обрабатывается иначе: старый сокет читается до
приветствия нового, а подписки повторно не создаются. Потерю подписки дополнительно
обнаруживает периодическая проверка списка подписок Twitch.

Временная недоступность сети или прокси не ограничена тремя попытками. Повторные
подключения продолжаются с увеличивающейся паузой до 60 секунд. Невосстановимая
авторизация остаётся явно видимой как `AUTH_REQUIRED`.

При неожиданной смерти критической задачи остальные задачи отменяются; процесс
выходит с ненулевым кодом. `runtwitchbot.bat` перезапускает такой процесс через
20 секунд. Ошибка конфигурации (код 2) и второй экземпляр в той же папке (код 3)
не запускают бесконечный цикл. `Ctrl+C` предназначен для остановки. Две разные
копии проекта блокировкой одной папки не защищены — запускай одну рабочую копию.

Twitch не воспроизводит события, пропущенные при обычном разрыве связи. Компьютер
должен оставаться включённым и не спать; бот не меняет настройки питания и не
обещает непрерывную работу выключенного Windows.

Входящие события других каналов и сообщения из чужого источника Shared Chat
игнорируются. Но **сам Twitch пересылает исходящие сообщения user-token-бота во
все каналы активной Shared Chat-сессии**. Этот проект не обходит такое поведение:
`for_source_only` с user token запрещён API. Строгая изоляция исходящих сообщений
при Shared Chat потребовала бы отдельной app-token схемы авторизации.

Актуальные команды проверки и датированный результат описаны в
[документе о тестировании](docs/TESTING.md). Для проверки реальной доставки
предусмотрен `check-chat.bat`.

## Безопасность и данные

`data/tokens.db` сохраняет исходные таблицы `tokens` и `messages`. Добавлены
`fgp_seen` и `fgp_probes`; миграция не удаляет старые токены и журнал. Обновлённая
пара OAuth сохраняется до следующего сетевого запроса. Compare-and-swap защищает
от затирания одновременной ручной авторизации фоновым refresh.

Логи: `logs/fgpbot.log`, ротация примерно 2 MiB × 5 файлов. OAuth-секреты передаются
в теле запроса, не в URL. Форматтер очищает готовые строки, включая traceback.
Тексты чата в обычный операционный лог не пишутся; при включённом журнале они
сохраняются в SQLite.

**`.env` и база OAuth не зашифрованы.** Защищай папку правами Windows и не публикуй
её вместе с резервными копиями. Gitignore не удаляет секреты, уже попавшие в историю
Git, и новый форматтер не очищает старые логи.

`.env`, `data/`, логи, базы SQLite, ключи и резервные копии исключены через
`.gitignore`. Перед коммитом локально установи hooks командой
`prek install --hook-type pre-commit --hook-type pre-push` и запускай Gitleaks;
в CI он проверяет историю Git. Если секрет был раскрыт, отзови и замени его у
провайдера: удаление файла или коммита не отзывает выданные права.

Подробнее: [архитектура](docs/DESIGN.md) и
[тесты и границы проверки](docs/TESTING.md).
