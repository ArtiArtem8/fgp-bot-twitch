# Архитектура: маленькое локальное приложение, а не сервисная платформа

## Выбранный подход

Один процесс, одна конфигурация канала, одна база SQLite и общий HTTP-клиент.
Официальная модель Twitch — EventSub для приёма событий и API для отправки —
сохранена. Убрана зависимость от внутренних реализаций TwitchIO, а не сам протокол.

Для этого проекта важнее понятный путь исполнения и проверяемые отказы, чем
динамическая загрузка расширений, универсальные репозитории, контейнер внедрения
зависимостей или инфраструктура развёртывания.

## Границы модулей

```text
main.py → cli.py
               ├─ auth.py → Tokens.validate → Store.save_token
               ├─ status / doctor / check-chat / selftest
               └─ app.py: Application
                     ├─ EventSub → bounded queue → Commands → Twitch.send
                     ├─ Tokens ↔ Store (SQLite)
                     ├─ audit: реальная подписка текущей сессии
                     ├─ probes: одноразовая локальная заявка и проверка echo
                     └─ Health → atomic status.json

network.Http → aiohttp session → явно настроенный proxy
security.SafeFormatter → консоль / rotating log
```

`config.py` знает настройки и пути. `tokens.py` владеет валидацией, обновлением и
кэшем токенов. `twitch.py` знает небольшую используемую часть Helix. `eventsub.py`
владеет жизненным циклом сокета, но не выполняет команды. `commands.py` не зависит
от конкретного WebSocket и получает обычные данные событий. `storage.py` единственный
владелец SQL. `health.py` описывает наблюдаемое состояние, не симулируя успешную работу.

Это явная композиция объектов в точке запуска, не DI-фреймворк. Небольшое количество
объектов позволяет заменить сетевую границу имитатором, не переписывая бизнес-логику.

## Почему без TwitchIO в этой версии

Сохранение стабильного TwitchIO с документированными точками расширения тоже было
бы разумным вариантом. Библиотека сама по себе не является причиной инцидента.
Проблемой стали логика подписок и собственная обвязка вокруг её приватных клиентов,
сессий и менеджера токенов.

Для набора из нескольких команд одного канала выбрана узкая самостоятельная
реализация. Теперь нет копии внутреннего OAuth-клиента, рефлексивного загрузчика
компонентов, `asqlite`-обвязки и внешнего генератора трёх групп ответов.

**Цена решения:** логика EventSub и OAuth теперь поддерживается в этом проекте,
а не обновляется вместе с TwitchIO. Исходных строк не обязательно стало меньше:
добавились диагностика, восстановление, защита состояния и тесты. Это уменьшение
скрытой сложности и числа прямых зависимостей, не доказанный выигрыш памяти или CPU.
При заметном росте функциональности/числа каналов стоит заново оценить использование
готового SDK вместо расширения собственного протокольного слоя.

## Основные проектные решения

### Готовность по наблюдаемым условиям

Запущенный процесс, успешная OAuth-валидация, подключённый транспорт и сквозной
ответ — разные утверждения. `Health` хранит их отдельно. API-доступность никогда
не заменяет активную чат-подписку. Отсутствие сообщений зрителей не считается сбоем;
молчание определяется по служебному keepalive, а не активности аудитории.

Сквозная проверка — явный opt-in. Локальная команда записывает одноразовую заявку
в SQLite, а работающий процесс отправляет сообщение и сверяет его EventSub echo.
Постоянный публичный спам «проверками здоровья» не нужен. Проверка доказывает путь
одного сообщения, не вечную доступность и не работоспособность внешнего music API.

### Структурированная конкурентность

Критические задачи принадлежат одному `asyncio.TaskGroup`. Если обработчик или
запись состояния неожиданно падает, остальные задачи не продолжают создавать
иллюзию полноценного бота. Ошибка поднимается к процессу и видна BAT-перезапуску.

Получение кадров сокета отделено от обработки команд ограниченной очередью.
Иначе медленная музыка или SQLite могли бы задержать обработку keepalive.
Последовательная обработка команд — сознательная простота для одного канала;
медленная команда может задержать следующие. Очередь ограничена, старые события
не воспроизводятся бесконечно, переполнение видно в диагностике.

### Владение токенами и состоянием

Токен принадлежит конкретному user ID и Client ID. Чат использует только токен
бота, followage может использовать дополнительный токен владельца. Ошибка необязательной
функции не должна запрещать `!ping` или ссылки канала.

Новая пара access/refresh фиксируется до следующей валидации. SQL compare-and-swap
не позволяет фоновому обновлению затереть более новую ручную авторизацию. Повторный
невалидный refresh не выполняется каждую минуту до изменения пары или перезапуска.
База — источник истины, кэш периодически перепроверяется и сверяется с сохранённой парой.

SQLite работает через стандартную библиотеку и `asyncio.to_thread`, без общего
соединения между потоками. Изменения транзакционные. Никакие хранилища или брокеры
за пределами локальной машины не требуются.

### Ограниченные повторы, а не «попробовать всё ещё раз»

GET можно безопасно повторить ограниченное число раз. После тайм-аута POST нельзя
знать, дошёл ли запрос: автоматическая повторная отправка могла бы дублировать чат.
Исключение — полученный 401, то есть явный отказ до выполнения операции: допускается
одна повторная попытка авторизации.

Дедупликация — защита от повторного запуска известного события, **не гарантия
exactly-once**. Маркер фиксируется перед побочным эффектом. Если процесс упадёт между
фиксацией и отправкой, ответ может быть потерян; этот вариант выбран вместо повторной
публикации после перезапуска. Для обычного чат-ответа это предпочтительнее неожиданного
повторного приветствия или серии дубликатов.

### Простая эксплуатация

`python main.py` и `runtwitchbot.bat` сохранены. Относительные пути не зависят от
текущего каталога Планировщика. Секреты остаются в прежнем `.env` и `tokens.db`;
мониторинг доступен локальной командой, без веб-панели.

Установка отделена от запуска. Совместимые диапазоны зависимостей в pyproject не
являются полной фиксацией окружения. `uv sync` создаёт локальный `uv.lock`; после
проверки на рабочей машине его стоит сохранить в репозитории. В поставку не включён
фиктивный lock-файл или непроверенная копия окружения. Повторный `setup` может выбрать
более новые версии в разрешённых диапазонах; обычный запуск ничего не обновляет.

## Чего сознательно нет

Нет контейнеров, Redis, отдельного сервера мониторинга, ORM, динамического каталога
плагинов, фонового автоматического деплоя и универсального механизма восстановления
всех команд после сбоя. Нет отправки отчётов в сторонний сервис и скрытого тестового
аккаунта Twitch. Нет отключения TLS-проверки ради работы прокси.

Эти ограничения соответствуют задаче: один локальный бот должен работать для одного
канала, явно показывать отказ и не требовать постоянного ручного захода на Twitch.
