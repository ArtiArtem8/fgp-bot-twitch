`fgp-bot-twitch-code-20260923-170342.tar(1).zst` и лог запуска из сообщения.
SHA-256 исходного архива:
`e9e28e6a87f191a95ba19643a04f055238087fc3dcffc2faefe72418df3fc549`.

Номера строк ниже относятся к **исходной версии в архиве**, не к новой версии.
Разбор оригинала выполнен по исходникам и предоставленному логу; оригинальный

## Главная причина молчания

Успешная авторизация и работающий HTTP API не подключали бот к чату.

В `main.py:225–238`, `Bot.setup_hook`, подписки намеренно не создаются.
В `main.py:240–275`, `event_token_added`, токен самого бота заканчивает обработку
ранним `return`. Подписки создаются только после успешной загрузки другого
пользовательского токена, в данном запуске — токена стримера.

В логе бот `1293258394` успешно обновляет свою авторизацию. Для `494679299`
валидация возвращает 401, обновление — 400, и загрузчик пропускает эту запись.
Затем процесс выводит `Bot ready`, хотя ветка подключения EventSub не выполнялась.
Далее видны запросы к `/helix/users`, но не создание подписок или события чата.
Это согласуется с жалобой стримера, а не опровергает её.

Новая версия создаёт подписку на один настроенный канал после приветствия каждого
нового WebSocket. Для чтения и отправки используется токен самого бота с
`user:read:chat` / `user:write:chat`. Токен стримера не является обязательным условием
основной работы. Сценарий с нерабочим owner token покрыт интеграционным тестом на
локальном имитаторе Twitch.

## Дополнительные меры надёжности

Входящая очередь ограничена; переполнение и просроченные события отражаются в
счётчиках и состоянии, а не скрываются. Получение WebSocket-кадров не ждёт
музыкального API и обработчиков команд. Тексты и ответы ограничиваются по длине.

Обычная потеря сокета и штатный перенос соединения Twitch разделены. При штатном
переносе старое соединение читается до готовности нового; перенесённые подписки
не создаются повторно. Тест выявил и закрыл случай, когда старое соединение успевает
закрыться до нового welcome. Повторное событие не вызывает повторный ответ.

Безопасные GET допускают ограниченный повтор. Неоднозначно завершившийся POST
отправки не повторяется автоматически: потерянный HTTP-ответ не доказывает, что
сообщение не было опубликовано. Отказ `is_sent=false` не считается отправкой.

Статус пишется атомарно. Завершение ожидает уже начатую запись, чтобы поздний
`READY` не перезаписал финальный `STOPPED`. Невосстановимый сбой рабочей задачи
не оставляет здоровую на вид задачу мониторинга жить отдельно.

## Осознанные изменения поведения

Это новая реализация рабочего ядра, не минимальный патч совместимости TwitchIO.
Сохранены точка входа, имя BAT, имена основной конфигурации и схема данных.
Старые компоненты не загружаются автоматически: команды регистрируются явно.

Шуточные баны имеют другой, более простой набор фраз; принадлежность цели текущему
списку чаттеров больше не проверяется. Music queue показывает непрослушанные треки.
Followage сообщает отсутствие прав, не выдавая его за отсутствие фолловинга.

Канал зафиксирован конфигурацией, а не списком всех токенов в базе. Однако платформенное
поведение Shared Chat для исходящих user-token сообщений остаётся: см. README.

## Что подтверждено и что не подтверждено

**117 автоматических тестов прошли**, включая реальные локальные HTTP/WebSocket
соединения, OAuth callback и SQLite. Подробности и метрики — в `TESTING.md`.
Это не live-тест Twitch и не нативный прогон Windows.

Не проверены права нынешних аккаунтов, состояние конкретного Hiddify, контракт
живого музыкального сервиса, ограничения модерации канала и поведение Windows
при сне/пробуждении. Новый `check-chat --send` предназначен для проверки основного
пути на рабочей машине после установки и безопасной переавторизации.

Ни оригинальная папка на Windows, ни GitHub-репозиторий этим архивом автоматически
не изменены. Действующие секреты не использовались для обращений к Twitch.
